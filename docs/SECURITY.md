# Security model and implementation limits

Every route must authenticate the caller and derive the owner from the validated server session. Client-supplied user identifiers are never authorization. The store always filters by owner; Supabase independently enforces read isolation through RLS, checks JSON ownership against relational ownership, and denies direct client mutation of privileged records. Server service keys are trusted credentials: keep them out of browser bundles, logs, and public files.

Local authentication is for development: salted scrypt hashes, random 256-bit sessions, hashed session lookup, HttpOnly SameSite cookies, and persisted rate limits. Supabase Auth handles production accounts and password storage. The server calls `auth.getUser()` to validate sessions. `user_metadata` is used only for display names and never for role or billing authorization.

OAuth credentials are encrypted separately from normal record tables. Local AES-256-GCM authenticates both the owner and secret reference; the master key is a mode-0600 file in the private data directory. Production uses Supabase Vault through service-only public invoker wrappers and private definer functions with a fixed empty search path. A caller cannot use another tenant's reference. Provider refresh/access tokens must never be sent to the model or the browser.

Application submission requires a resolved approval or explicitly scoped standing permission. Approval binds the profile, exact resume, answer contexts, and a fingerprint of the prepared form. Changed questions do not inherit answers solely from a field name; changed forms require new review. Unknown optional preselected values pause as well. A persisted submission latch and final field record precede the final click, including autonomous execution. The browser verifies field values and requires portal confirmation evidence before claiming a verified submission. Losing the browser response after clicking leaves `submission_unverified`; retrying cannot assume the application failed. Screenshots and exact submitted resumes live in private storage, scoped to their owner.

External pages, documents, repository READMEs, and emails are untrusted data. Content cannot grant tool permissions, create accounts, expand scopes, change billing, or authorize submissions. The agent only selects confirmed evidence. Sensitive or ambiguous screening answers require user confirmation. The application never infers immigration eligibility from nationality or school.

Browser navigation must validate URLs, redirects, DNS results, and each subsequent request. Production worker network policy remains essential against DNS rebinding and private network access. Deterministic provider adapters are preferred; unsupported or restricted portals stop for user action. CAPTCHA, MFA, anti-bot gates, and access controls are not bypassed. Browser sessions are per user; do not persist password strings or session state in application records.

Uploaded LaTeX is untrusted code. Custom templates may compile only in the isolated, network-disabled compiler described in `docs/RESUMES.md`; escaping or command filtering alone is not a sandbox. The web process does not execute user build scripts. Host compiler mode is limited to trusted built-in templates with escaped content in explicitly configured development.

Stripe webhooks require a valid signature, an atomic event claim, current subscription reconciliation, and persisted completion. The client cannot directly change plan entitlements or quota events. Retries do not count as new verified submissions; receipt evidence is required before recording usage.

Operator metrics require an exact user UUID match in `ADMIN_USER_IDS`. The page and API each gate access before reading global records. The API emits aggregate counts and pseudonymous customer hashes only. Keep the allowlist server-side; do not use user-editable metadata or email-domain membership as a substitute. The metrics endpoint has no mutation capability.

Before opening a beta, run the real Supabase RLS/integration tests and database advisors, validate provider OAuth approvals, verify worker egress restrictions and compiler isolation, set retention/deletion policies, and test backup restoration. These deployment checks are not replaced by passing local fixture tests. Live Supabase, Stripe, inbox providers, Browserbase, and employer submission behavior require credentials and staging validation.
